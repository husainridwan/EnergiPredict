# EnergiPredict

EnergiPredict is an end-to-end machine-learning application for forecasting
hourly HVAC electricity consumption. It was developed as a final-year project
for the B.Sc. Electrical & Electronics Engineering programme at the
University of Lagos.

The project answers a practical question: how accurately can standard machine-
learning models forecast building HVAC load using information available before
the forecast hour? The repository contains the data pipeline, feature
engineering, model training and evaluation code, serialized model artefacts, a
FastAPI service, and a browser interface for uploading data and downloading
forecasts.

## Important qualification

The included data is a proxy dataset from another building. It is not measured
from University of Lagos auditoriums. The results therefore demonstrate the
method and its behaviour on the source building; they are not calibrated
predictions of UNILAG consumption. Local deployment requires retraining and
validation against metered auditorium data.

## Results at a glance

The final report was generated by `energipredict.train` and is stored in
`reports/metrics.json`. The target is `hvac_total = hvac_N + hvac_S`, measured
as hourly mean kW. Since each interval is one hour, the numeric value is also
the kWh consumed during that hour.

The dataset contains 19,212 hourly observations from 2018-02-22 through
2020-05-02. It has complete hourly coverage, no duplicate timestamps, and no
interpolated target or weather values. The target has a mean of 42.08 kW, a
standard deviation of 22.174 kW, and ranges from 0 to 123.126 kW.

The deployed model is Ridge regression for the 24-hour horizon, selected by
validation RMSE. Gradient Boosting achieved the lowest held-out test RMSE,
7.43 kW, and improved on the 24-hour persistence baseline by 20.8%. The
stacking ensemble was not the best model on the held-out test set, so it is
not presented as the overall winner.

CV(RMSE) is RMSE divided by the mean load. The 24-hour Gradient Boosting test
CV(RMSE) is 22.09%, below the 30% reference threshold used in this project
from ASHRAE Guideline 14. This comparison is informative, not a certification
of the model or of a future UNILAG deployment.

## Methodology

### Data preparation

1. Read and sort the hourly source data by `date`.
2. Construct `hvac_total` by adding the north and south HVAC submeters.
3. Reindex onto a complete hourly timeline so row-based lags retain their
   intended meaning.
4. Interpolate gaps of up to three hours; leave longer outages missing.
5. Drop rows that do not have a complete target and feature history.

### Forecast-safe features

The pipeline creates 36 features for each horizon:

- Calendar values: hour, day of week, month, day of year, weekend flag, and
  cyclic sine/cosine encodings.
- Weather: air temperature, relative humidity, solar radiation, cooling and
  heating degree hours, temperature lags, and 24-hour weather summaries.
- Load history: target lags at 1, 2, 3, 24, 48, and 168 hours, plus 24-hour and
  168-hour rolling mean, standard deviation, minimum, and maximum.

Features are horizon-aware. For the 24-hour forecast, target lags shorter than
24 hours are withheld because they would contain information from after the
forecast was issued. Building-management sensors, non-HVAC meters, duplicate
weather channels, and derivable dew point are excluded. The weather values at
the target timestamp represent an optimistic weather forecast; the dataset
does not contain archived forecast values with which to measure forecast error.

### Evaluation

The timeline is split chronologically into 70% training, 15% validation, and
15% test data. No random split is used for the main results because adjacent
hours are correlated and random splitting lets future neighbours enter the
training set. Hyperparameter tuning uses expanding-window `TimeSeriesSplit`
folds and negative RMSE scoring.

The model families are linear regression, Ridge regression, Random Forest,
Gradient Boosting, XGBoost, LightGBM, CatBoost, and a chronological stacking
ensemble based on XGBoost, LightGBM, and CatBoost. Models are single-threaded;
parallelism is controlled at the search level to avoid nested oversubscription.

## Application

The FastAPI application provides:

- `/` - project overview
- `/predict` - upload an hourly CSV and download forecasts
- `/benchmarks` - validation and test comparisons
- `/method` - methodology and limitations
- `/health` - service and model status
- `/api/model` - deployed model metadata and required columns
- `/api/results` - generated metrics report
- `/api/sample.csv` - valid sample upload data
- `POST /api/predict` - JSON predictions or a CSV download

An upload must contain `date`, the weather columns `air_temp_set_1`,
`relative_humidity_set_1`, and `solar_radiation_set_1`, plus either both
`hvac_N` and `hvac_S` or a precomputed `hvac_total`. It must include enough
history to construct the longest lag and rolling features. The API rejects
invalid schemas, irregular timestamps, empty files, non-UTF-8 CSV files, and
uploads larger than 25 MB with actionable errors.

## Setup

Python 3.10 or newer is recommended. From the repository root:

```bash
python -m venv venv
source venv/bin/activate       # Linux or WSL
# venv\\Scripts\\activate      # Windows PowerShell
python -m pip install --upgrade pip
pip install -r requirements.txt
```

Start the API without the reload watcher:

```bash
uvicorn main:app --host 127.0.0.1 --port 8000
```

Open `http://127.0.0.1:8000` in a browser. On WSL, avoid `--reload` when the
watchfiles backend cannot allocate enough memory while scanning the repository.
The repository contains large model artefacts, so manual restarts are the most
reliable development option in that environment.

## Training and analysis

Train both horizons with the full search:

```bash
python -m energipredict.train
```

Useful alternatives:

```bash
python -m energipredict.train --quick
python -m energipredict.train --horizons 24
python eda.py
python benchmark_results.py
pytest
```

Training writes one artefact per learned model to `models/h1/` and `models/h24/`,
the API artefact to `models/deployed.joblib`, and the complete generated report
to `reports/metrics.json`. The report is the source of truth for the results
shown above.

## Limitations and next steps

- The source building is a proxy for UNILAG auditoriums; local metering is
  required before operational use.
- Measured weather at the target timestamp stands in for a real forecast, so
  deployed day-ahead accuracy may be lower.
- Occupancy, building-envelope characteristics, HVAC schedules, and setpoints
  are not available in the current dataset.
- Predictions are not causal explanations and should not be converted into
  Naira savings without a tariff and billing model.
- Models should not be trusted outside the temperature and load ranges seen in
  training.

The most valuable next step is to meter one auditorium for a full operating
term, add occupancy and schedule information, and retrain the same pipeline on
local data.
