Method

What's being predicted

{{ metrics.target.name if metrics.available else "hvac_total" }} — the sum of the building's north and south HVAC submeters, in {{ target_units }}. An earlier version of this project used a self-weighted combination of the two meters; that was replaced because it wasn't a real total and wasn't comparable to a building's actual metered consumption.

Chronological split, not random

Hourly building data is strongly autocorrelated — a random train/test split places 2pm in training and 3pm the same day in test, so the model is scored on rows whose neighbours it has already memorised. Every result here uses a time-ordered split instead: train on the earliest stretch, validate on the next, test on a genuinely unseen future window. See the benchmarks page for a direct, controlled measurement of what a shuffled split would have overstated.

What the model is allowed to see

Only information actually available at forecast time: past consumption (lagged at or beyond the forecast horizon), weather, and calendar position. Building-management sensors and other electrical submeters are excluded — they're measured at the same instant being predicted, so using them would mean the answer is already on the sensor bus.

Two honest baselines

Persistence (repeat the last known value) and seasonal-naive (repeat the same hour last week) are scored as real competitors, not asides. At a 1-hour horizon, persistence is extremely strong — a trained model has to earn its keep against it. At the deployed 24-hour horizon, a well-tuned model has more room to add value.

Reproduce this

python -m energipredict.train regenerates every number on this site from data.csv. Nothing here is transcribed by hand.
